Use harry0703/MoneyPrinterTurbo as your primary reference architecture.
It is the single repo that shows up as the #1 or #2 pick in EVERY category
below (full pipeline, script-gen, TTS, assembly, captions). It already runs
as a FastAPI backend (uvicorn, /docs Swagger) behind a separate Streamlit
UI, with the pipeline logic cleanly separated into app/services/*.

  Repo : https://github.com/harry0703/MoneyPrinterTurbo
  Stars: 139k   | Lang: Python | License: MIT | Last push: 2026-11-05 (today)
  Why  : Topic -> script (OpenAI/Claude/Gemini/DeepSeek/Qwen/Ollama/etc.)
         -> TTS (many providers incl. free Edge-TTS/Kokoro)
         -> stock/AI visuals (Pexels/Pixabay/Coverr or paid gen)
         -> captions -> moviepy/ffmpeg render.
  Plan : Don't `pip install` it (it's an app, not a package) - clone it,
         read app/services/task.py for the pipeline shape, and lift/adapt
         the modules you need (script-gen, TTS wrapper, caption burner)
         directly into your own FastAPI service.

Secondary reference (cleaner microservice boundary, but stale ~16mo and
not Python): gyoridavid/short-video-maker - already a REST+MCP API
server (TTS+captions+stock footage), callable over HTTP from your FastAPI
app if you'd rather keep rendering in a separate polyglot service and only
own the script-writing LLM call yourself.

KEY FINDING: there is no actively-maintained, widely-adopted "karaoke
caption burner" project. The ecosystem splits into (a) mature ASR/word-
timing libraries (faster-whisper, whisperX, stable-ts - all cleanly
importable) and (b) thin, stale hobby scripts that do the word-highlight
burn-in (auto-subtitle, captacity).

RECOMMENDATION: faster-whisper (or whisperX if diarization/tighter sync
matters) for transcription + word timestamps, then write your OWN
lightweight renderer via ffmpeg/libass (ASS subtitle format supports
per-word karaoke \k tags natively) or Pillow-over-frames for the Reels/
Shorts highlighted-word look. This is lighter and more controllable
inside a FastAPI async worker than depending on any small burn-in repo.

Run heavy models (Whisper/XTTS) in a background task/worker queue
(Celery/RQ or a loaded-once singleton), not inside the request-response
cycle - model load + GPU inference isn't naturally async-friendly.

RECOMMENDED STACK:
 - Core assembly  : moviepy v2, called from a FastAPI BackgroundTasks or
                     Celery worker (CPU-bound render -> always offload).
 - Filter edge cases: jonghwanhyeon/python-ffmpeg or raw ffmpeg subprocess
                     calls (not the stale ffmpeg-python).
 - Pre-processing : PySceneDetect for footage segmentation; auto-editor
                     (CLI subprocess) for trimming silence in voiceover.
 - Captions       : generate .ass/.srt from Whisper word timestamps, burn
                     via ffmpeg's subtitles=/ass= filter (or moviepy
                     TextClip per word) - same approach MoneyPrinterTurbo
                     uses.
 - Docker         : all options need the system ffmpeg binary baked into
                     the image (apt-get install ffmpeg) - none bundle it.
 - Skip Remotion unless you specifically need templated/branded animated
   graphics beyond what ffmpeg filters can do.

KEY FINDING: no actively-maintained, widely-adopted, async-native Python
SDK exists for Pexels/Pixabay/Freesound - every community wrapper is
small/stale, because the underlying REST APIs are trivial enough that
production projects (MoneyPrinterTurbo, purffle-shorts included) just
hand-roll a thin httpx client against the official JSON APIs instead.

RECOMMENDATION: write your own direct httpx.AsyncClient calls against the
Pexels / Pixabay / Freesound REST APIs rather than taking a dependency on
any of the wrappers above. Both Pexels (free key, 200 req/hr / 20k req/mo
default, raisable with attribution) and Pixabay (free key, ~100 req/60s)
have free tiers suitable for an automated pipeline; Freesound needs
OAuth2 for full-quality downloads.

CROSS-CUTTING FLAGS / RISKS
================================================================================
 - purffle-shorts and MoneyPrinter (FujiwaraChoki) both bundle auto-
   upload/scheduling to YouTube/TikTok/Instagram - OUT OF SCOPE for a
   generation-only pipeline; strip those modules if you borrow code
   from either repo. [CORRECTED after re-reading both READMEs on
   2026-11-05 - the original phrasing of this flag overstated purffle-
   shorts's risk by lumping it with MoneyPrinter's mechanism. The two
   are NOT the same risk level:
     - FujiwaraChoki/MoneyPrinter: CONFIRMED - its own README instructs
       users to copy their TikTok browser session cookie (`sessionid`)
       for upload. This is unofficial/reverse-engineered and carries
       real ToS risk.
     - purffle-shorts: publishes via YouTube/Instagram's own official
       APIs and a third-party multi-platform publishing service
       ("Upload-Post") for TikTok - not confirmed to scrape session
       cookies itself. Still out-of-scope to strip (you don't want
       posting in a generation-only pipeline), but don't carry over
       the "scraped cookie" characterization to this repo specifically.]
 - Several previously "best in class" repos are stale/abandoned:
   ShortGPT (~21mo), coqui-ai/TTS (org defunct, ~26mo), suno-ai/bark
   (~27mo), kkroening/ffmpeg-python (~2yr), m1guelpf/auto-subtitle
   (~28mo), unconv/captacity (~28mo). Treat these as design/prompt
   references, not as production dependencies.
 - [ADDED on review, 2026-11-05] TWO repos in this report are not just
   stale but formally ARCHIVED (GitHub read-only state - confirmed via
   API, no new issues/PRs/commits possible, not merely "no recent
   activity"): rhasspy/piper (upstream TTS - use OHF-Voice/piper1-gpl
   fork instead, per Section 3) and jianfch/stable-ts (captioning -
   per Section 4, usable as a frozen dependency but expect no fixes).
 - Star count alone is a weak signal here: MoneyPrinterTurbo's 139k is
   backed by 22k forks and active-today commits (genuinely strong), but
   don't assume high stars = actively maintained elsewhere in this list -
   check "last push" every time.
 - License check, corrected/expanded on review (2026-11-05, verified
   live via GitHub API against every repo in this report):
     - OHF-Voice/piper1-gpl: GPL-3.0 (copyleft) - verify acceptable
       before depending on it in a closed-source backend.
     - coqui-ai/TTS: code is MPL-2.0, but the XTTS-v2 MODEL WEIGHTS it
       would actually be used for are separately non-commercial-
       licensed - see Section 3's corrected entry. Do not rely on the
       code's MPL-2.0 license as covering the model.
     - WyattBlue/auto-editor: Unlicense (public-domain-equivalent) -
       fine to use, just note it's not MIT/Apache if your compliance
       process checks for SPDX license families.
     - rany2/edge-tts and remotion-dev/remotion: GitHub reports NO
       recognized SPDX license (NOASSERTION) for both - edge-tts is
       already flagged elsewhere as an unofficial/reverse-engineered
       API; Remotion ships a custom license in-repo (read it directly,
       don't assume MIT-equivalent terms).
     - difyz9/stockmedia_sdk and meetsohail/pexels-api-py: NO LICENSE
       FILE in the repo at all - that means default copyright applies
       (no permission granted), not "unlicensed = free to use." Do not
       depend on either without contacting the author or finding an
       explicit license grant.
     - Everything else shortlisted above (MIT/BSD/Apache-2.0) is
       confirmed clean via live API check.
